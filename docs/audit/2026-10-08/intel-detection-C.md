## (c) Tenant / RBAC issues

1. **ueba.py:17-21 and ueba/ingest.py:25-29 `_org_filter` returns `True` when org_id is None.** A user with no organization sees every tenant's entities, alerts, events, peer groups, dashboard and heatmap (ueba.py:162, 478, 838, 896, 1293-1376, 1416). Worse, for such a user `auto-cluster` (ueba.py:1004-1006, 1022-1030) deletes and re-buckets peer groups across all tenants, mixing tenants into groups with `organization_id=None`. `baselines/rebuild` (ueba.py:1171) rebuilds every tenant's baselines, and ingest matches any tenant's entity by `entity_id` (ingest.py:172-178).
2. **ueba.py:645-660:** the escalate create branch builds an `Incident` without `organization_id` (the column exists and is nullable). The result is an orphan incident that is invisible to the tenant or leaks across tenants, and on_incident_created still runs with the org id (ueba.py:671-676).
3. **ueba.py:615-617:** the entity lookup for escalation has no org filter. Low risk, because the alert is already org-scoped.
4. **BehaviorBaseline has no organization_id column** (ueba/models.py:84-121). Rows written at ueba.py:1228 and ueba/tasks.py:306 are tenant-less, and GET /ueba/baselines/{id} crashes with a 500 (ueba.py:1117).
5. **No RBAC on any UEBA route** (all of them use only `CurrentUser`). A viewer can change alert status (ueba.py:533), escalate and create incidents (ueba.py:573), delete and rebuild peer groups (ueba.py:978), wipe and rebuild baselines (ueba.py:1130), ingest events (ueba.py:692/735), create peer groups (ueba.py:911) and toggle the watchlist (ueba.py:222).
6. **ITDR RBAC:** only `/threats/{id}/respond` enforces `_require_analyst` (itdr.py:613). A viewer can create and update identities (itdr.py:193/211), create, update or investigate threats (itdr.py:367/403/423), run the scan (itdr.py:695), check and remediate exposures (itdr.py:983/1097), and approve or revoke elevation (itdr.py:1376/1413). Approve also lacks an approver-role check and self-approval prevention.
7. **itdr.py:367-381 create_threat** does not check that `identity_id` belongs to the caller's org, so a threat can be FK-linked to another tenant's identity.
8. **ITDR list, scan and metrics use `if org_id:`, which skips the filter when org_id is None.** Affected: itdr.py:129-130, 309-310, 725-727, 920-921, 1186-1187, 1305-1306, 1466-1471, 1558-1559. A user with no org sees all tenants, and `/threats/scan` scans every tenant and writes threats with `organization_id=None` (itdr.py:752-753). The single-row getters use `if org_id is not None` (itdr.py:76, 93, 971, 1237), which is the same gap.
9. **itdr/tasks.py:308-312** (dead task): the CredentialLeak query has no org filter.
10. **itdr.py:236-260 risk-score:** the child counts filter by identity_id only. That is acceptable because the identity is org-verified at itdr.py:238.
