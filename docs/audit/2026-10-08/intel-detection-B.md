# Audit rows B — SIEMDashboard.tsx + ThreatHunting.tsx (siem / hunting domains)

Notes:
- Neither page imports components from frontend/src/components; both use `api` from frontend/src/lib/api.ts with inline calls.
- `DatabaseSession` = plain `get_db` (src/core/database.py:77). There is no global tenant filter (no `do_orm_execute` or RLS hook; `get_tenant_db` at src/api/deps.py:30-35 is a no-op). Any query without `.where(organization_id == ...)` therefore returns data from every tenant.
- **Systemic "NULL-org then 404" bug.** The create paths for detection rules (siem.py:740-756), Sigma imports (siem.py:1294-1311), data sources (siem.py:1041-1048), the built-in rule seeder (rule_seeder.py:384-404), hypotheses (hunting.py:475-487), template instantiation (hunting.py:1064-1074), sessions (hunting.py:607-612), executor findings (hunting.py:200-215, 241-254, 277-293, 315-330) and manual findings (hunting.py:845-855) never set `organization_id`. The per-ID helpers then add `organization_id == org_id` whenever the user has an org (siem.py:63-64, 78-79, 108-109; hunting.py:55-56, 72-73, 89-90). Result: a user who belongs to an org gets 404 on every follow-up action against rows that user just created.
- Verified by a read-only probe (scratchpad/audit_intel/s/corr.py and corr2.py). After 3 distinct destinations from one source IP, `CorrelationEngine.process_event` returns a SessionCorrelation result on **every** later event, and its severity is an Enum, so `severity in ("high","critical")` is False. Inserting the `CorrelationEvent` that the pipeline builds fails, first on the Enum bind and then with `NOT NULL constraint failed: correlation_events.correlation_id`.

## (c) Tenant / RBAC issues

Tenant isolation (no `organization_id` filter; DatabaseSession is unscoped):
1. src/api/v1/endpoints/siem.py:427-505 `search_logs`: every tenant's logs (also used by Live Tail).
2. siem.py:508-552 `aggregate_logs`: no org filter.
3. siem.py:555-655 `get_siem_stats`: every count and chart spans all tenants.
4. siem.py:675-730 `list_rules`, siem.py:953-978 `list_correlations`, siem.py:1018-1032 `list_sources`: unscoped lists.
5. siem.py:60-117 `get_*_or_404`: skip the org filter when `org_id is None`, so an org-less user can read, modify or delete any tenant's log, rule, correlation or source. Same pattern in saved searches (siem.py:1109, 1154, 1174, 1183) and hunting (hunting.py:55, 72, 89).
6. Create paths never set organization_id: siem.py:740-756 (rules), 1294-1311 (import), 1041-1048 (sources); src/siem/rule_seeder.py:384-404; hunting.py:475-487, 1064-1074, 607-612, 845-855, and executor findings at 200-330. Org users then get 404 on their own rows.
7. src/siem/engine_manager.py:40-72 + pipeline.py:146-153: one global RuleEngine holding all tenants' rules, evaluated on all tenants' logs. Tenant A's custom rule raises alerts in tenant B.
8. src/siem/correlation.py:158-162, 246-250 + engine_manager.py:31-37: correlation buffers are keyed without org, so events from different tenants correlate together.
9. pipeline.py:189-192: `match_count` UPDATE is keyed by `DetectionRule.name` only, so it bumps same-named rules in every tenant.
10. hunting.py:189-192, 228-233, 262-263, 300-301 (executor): hunts other tenants' LogEntry, ThreatIndicator, Alert and AuditLog rows.
11. hunting.py:400-465, 630-681, 775-829, 1478-1558: hypotheses, sessions, findings and stats lists are unscoped.
12. src/hunting/models.py:331+ `HuntNotebook` has no organization_id column. hunting.py:101-112 `get_notebook_or_404` has no tenant check, so get/update/execute-cell/publish/export are IDOR across tenants. Execute-cell `logs`/`ioc` (hunting.py:1251-1258, 1276-1278) are unscoped.
13. hunting.py:948-958: the escalated Incident is created without organization_id.
14. siem.py:383: `/logs/batch` trusts the body `organization_id` when the user has no org.
15. siem.py:1443-1476: syslog logs are stamped with `SIEM_DEFAULT_ORG_ID` or the sole superuser's org. In a multi-tenant deployment every syslog event goes to one tenant (or NULL).
16. src/siem/mirror.py:261, 386: mirrored audit and detection rows get `organization_id: None`.
17. src/siem/cloud_poller.py:570-575 via siem.py:1378: the manual poll iterates all tenants' integrations and returns their ids and outcomes to the caller.

RBAC (all use plain `CurrentUser`; no role or permission checks):
18. siem.py:1554, 1593: any authenticated user can start or stop the process-wide syslog listener.
19. siem.py:1378 (cloud poll-all) and siem.py:1404 (global backfill): admin operations open to any user.
20. siem.py:733, 782, 813, 1213: any user can create, modify, delete or import detection rules and force a global engine reload.
21. siem.py:1035, 1058, 1082: any user can change data sources.
22. siem.py:46: `/siem/ingest/status` has no authentication at all.
23. hunting.py:911: any user can escalate to an incident. No RBAC on any hunting mutation.

Other correctness:
24. siem.py:1475: `logger.warning("…", error=str(exc))` on a stdlib `logging` logger raises TypeError, so the syslog default-org resolution failure crashes the batch handler.
25. Schema drift: alembic/versions/001_initial_schema.py:294-301 defines `correlation_events` as (id, event_data, correlated_at) and no later migration alters it. The model (src/siem/models.py:237-298) differs completely, so the table works only if `init_db` create_all (src/main.py:68) ran before alembic created it.
