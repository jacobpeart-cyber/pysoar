# Connectors

This page lists every entry in the integration catalogue (`GET /api/v1/integrations/connectors`) and what it can do in this release. The catalogue is built from the code: `BUILTIN_CONNECTORS` in `src/integrations/engine.py` names the vendors, and for a connector with a class in `CONNECTOR_CLASS_MAP` (`src/integrations/connectors/`) the actions, fields, test call and verification statement come from the class attributes `ACTIONS`, `CONFIG_FIELDS`, `CREDENTIAL_FIELDS`, `TEST_CALL` and `VERIFICATION`. `tests/unit/test_connector_catalog_truth.py` fails if the two drift.

## Status

* **implemented** (16): a connector class ships. Install validates the declared required fields (422 `missing_fields` / `invalid_fields`, naming fields, never values), credentials are stored AES-256-GCM encrypted (`enc:v1:` envelope) and never returned, the declared actions are mirrored into `integration_actions` with their real `input_schema`, `POST /installed/{id}/test` runs the connector's read-only call, and `POST /installed/{id}/actions/{action_id}/execute` validates `input_data` against the action's `params_schema` (422 `invalid_parameters`) before calling the vendor.
* **log_ingest** (4): no connector class; the SIEM cloud poller (`src/siem/cloud_poller.py`) reads the stored credentials and pulls events on a schedule (the vendor SDK for the three clouds, the pinned REST client for QRadar). Installable, no actions; the connection test answers 501 because the poller records `health_status` on every poll.
* **planned** (25): catalogue entry only, kept so the roadmap is visible. `installable: false`, no actions; install, test and execute answer 501 `{"error": "not_implemented", "detail": "<name> has no connector implementation in this release"}`. A row installed before this release reads `health_status: "unavailable"` and can still be deleted. The hourly health task records it `unavailable` without any network call.

`ingest: true` in a catalogue response means the SIEM cloud poller (`src/siem/cloud_poller.py`, Celery beat task `siem.poll_cloud_integrations`, and `POST /api/v1/siem/cloud/poll-all` for the caller's organisation) pulls that connector's events into the SIEM: the four `log_ingest` sources (AWS CloudTrail, Azure Activity Log, GCP Cloud Logging, IBM QRadar) and the two implemented connectors that also have a poller (Splunk, Elastic). Splunk, Elastic and QRadar polls go through `PinnedTransport` with TLS verification always on and redirects not followed; Splunk and Elastic polls reuse the connector classes. The `verify_tls` / `ca_bundle` opt-out of earlier releases is gone: a stored row that still carries either key is polled with verification on, and the poll records `verify_tls/ca_bundle are no longer honoured` in the integration's `error_message` (alongside a failure reason when the poll fails).

### On-premises targets

Outbound integration calls refuse a target that resolves to a private address (RFC 1918, IPv6 ULA `fc00::/7`, `100.64.0.0/10` and the other non-global unicast ranges). On-premises Splunk, Elasticsearch and QRadar normally live on such networks, so the operator opens them with `OUTBOUND_PRIVATE_ALLOWLIST` (a list of CIDRs in the API, worker and scheduler environment; see [docs/install/environment.md](../install/environment.md)). It is default deny and operator-level: tenants cannot change it, and it is read on every call. An address inside a listed network is allowed; loopback, link-local (`169.254.0.0/16`, `fe80::/10`), the cloud metadata addresses (`169.254.169.254`, `fd00:ec2::254`), multicast, unspecified (`0.0.0.0/8`, `::`) and reserved addresses stay refused whatever the list says, and every address of a DNS answer must pass. The list applies to every caller of `src/integrations/netguard.py` (connectors, the SIEM pollers, the generic HTTP action, OIDC / SAML metadata, directory sync, intel lookups). A refused private target of Splunk, Elastic or QRadar reports `refused: target resolves to a private address; add its network to OUTBOUND_PRIVATE_ALLOWLIST to allow it`, without the resolved address; other connectors keep reporting `refused: target resolves to an internal address`.

`rating`, `is_community` and `last_updated` in a catalogue response are not marketplace statistics (there is no marketplace service): they are always `null` / `false` / `null`. `install_count` is the calling organisation's installs of that connector (0 or 1).

## Transport and errors

Every HTTP call of an implemented connector goes through `PinnedTransport` (`src/integrations/netguard.py`): the vendor host is resolved once, internal, loopback, link-local, metadata and reserved addresses are refused, the connection goes to the vetted IP with the hostname in Host and TLS SNI, TLS verification stays on and redirects are not followed. A refused target is reported as `refused: target resolves to an internal address` (Splunk, Elastic and QRadar name the allow-list setting instead, see On-premises targets). AWS Security Hub uses boto3 against AWS regional endpoints; the region is validated against the AWS region format. Only GET and HEAD requests are retried (three attempts) (on 429, 502, 503, 504 and connection errors).

A vendor error is a `failed` execution with the vendor's HTTP status (`http_status`) and a sanitised message (whitespace collapsed, known secret values and bearer / basic tokens redacted, at most 200 characters); an API that reports failure inside a 200 (Slack `ok: false`, a CrowdStrike `errors` list, a PagerDuty event without `status: success`) is also `failed`. An action name the connector does not declare is `failed` with `unknown action X; available: [...]` and no execution row (an execution row needs a real action row).

### Connector notes

* **Okta**: `domain` is the org hostname only (`acme.okta.com`, `acme.oktapreview.com` or a custom domain); a scheme, path, port, `@`, `?`, `#`, whitespace or an IP literal is refused (422 `invalid_fields`) before any request. The token is sent as `Authorization: SSWS <token>`. `x-rate-limit-remaining` / `x-rate-limit-reset` are recorded and a call is refused locally while the bucket is known to be empty. `get_user` takes an id or a login (percent-encoded as one path segment); the other actions take the user id.
* **Microsoft Entra ID**: client-credentials token with scope `https://graph.microsoft.com/.default`. Each action's description names the Graph application permission it needs (User.Read.All, User.EnableDisableAccount.All, User.RevokeSessions.All, User-PasswordProfile.ReadWrite.All, AuditLog.Read.All, IdentityRiskyUser.Read.All / ReadWrite.All); the test call reads `/organization`, which needs Organization.Read.All or Directory.Read.All. `list_sign_ins` needs an Entra ID P1/P2 licence and `list_risky_users` P2. `reset_password` locks the current credential out: it sets a random password that is never returned, logged or stored, with `forceChangePasswordNextSignIn: true`; the user recovers through self-service password reset or the help desk. It also needs the app to hold a privileged Entra role that can reset that user's password. Values placed in `$filter` (user ids) must be GUIDs; text values have single quotes doubled.
* **Microsoft Defender for Endpoint**: client-credentials token with scope `https://api.securitycenter.microsoft.com/.default`; `geo` selects `api-<geo>.securitycenter.microsoft.com`, any other value is refused. Response actions return a machineAction with status `Pending`; `get_machine_action` reads its outcome. Each description names the WindowsDefenderATP permission (Machine.Read.All, Alert.Read.All, Alert.ReadWrite.All, Machine.Isolate, Machine.Scan, Machine.RestrictExecution, Machine.CollectForensics).
* **Microsoft Teams**: `webhook_url` must be https on `*.webhook.office.com` (Office 365 connector webhooks, being retired by Microsoft) or `*.logic.azure.com` (Workflows webhooks); anything else is refused before any request. Messages are Adaptive Cards in the documented `{"type": "message", "attachments": [...]}` envelope, sent without an Authorization header. The webhook has no read-only call, so Test posts a visible "PySOAR connection test" card to the channel; HTTP 200 or 202 is healthy (a 200 carrying an error text is not).
* **Splunk**: `base_url` is the management port (`https://splunk.example.com:8089`), https only, no path, query or credentials (422 `invalid_fields`). REST calls carry `Authorization: Bearer <token>` (a Splunk authentication token) or HTTP basic; install refuses neither (422 `missing_fields` names `token`, `username`, `password`). `search` is a one-shot job (`POST /services/search/v2/jobs`, `exec_mode=oneshot`; the v2 search endpoints need Splunk 9.0.1 or later) sent with both `max_count` and `count`; `search ` is prefixed unless the SPL starts with `search` or `|`. `run_saved_search` dispatches the saved search and therefore its alert actions. Saved-search names may contain spaces: a slash, backslash, `?`, `#`, `%` or a dot-segment is refused and the name is percent-encoded; a job sid goes through the plain-segment check. `hec_send_event` posts `{event, time, sourcetype, source, index}` to `{hec_url}/services/collector/event` with `Authorization: Splunk <hec_token>` and is refused before any request when `hec_url` or `hec_token` is unset; a non-zero HEC `code` is `failed`. The poller runs the `search` config value (default `search index=*`) over the poll window as `earliest_time` / `latest_time`, at most 1000 results per poll.
* **Elastic**: `base_url` is the Elasticsearch HTTP endpoint (`https://es.example.com:9200`), same URL rule. Requests carry `Authorization: ApiKey <api_key>` (the base64 `encoded` key) or HTTP basic; same either-or rule (`api_key`, `username`, `password`). Index names must match `^[a-z0-9][a-z0-9._-]{0,254}$` (no leading `_`, `-` or `+`, so system indices such as `_security` and `.security` cannot be named); `*` is accepted only by `search` and `count`; document ids go through the plain-segment check. All refused before any request. The poller searches `index` (default `logs-*`) for `timestamp_field` (default `@timestamp`) inside the poll window, oldest first, 500 documents per poll, and ingests each `_source`.
* **IBM QRadar**: no connector class, so no actions and no connection test (501). Install validates `base_url` (https origin) and `sec_token`. The poller sends `GET {base_url}/api/siem/offenses?filter=start_time>=<epoch ms>` with `SEC: <sec_token>`, `Version: 12.0` and `Range: items=0-499`; any non-2xx answer (a redirect included) records the integration `unhealthy` with the status and ingests nothing.

## Verification

None of these connectors has been exercised against a live vendor tenant in this repository: no vendor credentials are available to the project. Each implemented connector was written from the vendor's public API documentation (the endpoint is cited in a comment on each method) and is tested against faked vendor responses at the network boundary (`tests/unit/test_connector_test_connection.py`, `tests/unit/test_connector_actions_execute.py`, `tests/unit/test_connectors_identity_edr_chat.py`, `tests/unit/test_connectors_siem.py`). Hence every `verification` field reads "implemented from the vendor's public API documentation; not verified against a live tenant". In particular nothing in this release was exercised against a live Splunk, Elasticsearch or QRadar: the Splunk, Elastic and QRadar requests and pollers were written from the Splunk REST API reference, the Elasticsearch REST API reference and the QRadar API reference and are tested against faked responses only, and the operator allow-list is tested with steered DNS only.

An operator verifies a connector in their own tenant like this:

1. Install it from the Integrations page (or `POST /api/v1/integrations/install`) with the fields listed above. Use a least-privilege account: read scopes first.
2. Press Test (`POST /api/v1/integrations/installed/{id}/test`). The response names the read-only call in `details.checked`; `healthy` means the vendor accepted the credential for that call. `unhealthy` carries the HTTP status (`details.http_status`) and a sanitised reason, also stored as the integration's `error_message`.
3. Run one read-only action (no `*` above), for example VirusTotal `scan_ip`, Jira `get_issue`, CrowdStrike `search_hosts`, Okta `get_user` or Defender `get_machine`, from `GET /api/v1/integrations/installed/{id}/actions` and `.../actions/{action_id}/execute`, and compare the output with the vendor console. Only then grant write scopes and try a side-effect action on a test object.
